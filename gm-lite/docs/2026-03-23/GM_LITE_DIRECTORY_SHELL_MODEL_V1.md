# GM-LITE 目录外壳模型 V1

## 1. 核心判断

GM-LITE Light 当前不应优先走“重插件 UI”路线，而应优先采用：

> 目录规范作为产品外壳，  
> 共享任务总线作为运行时内核，  
> 命令脚本作为触发层。  

这意味着：

- 先不把精力耗在复杂 VSCode 插件壳上
- 先把规则、资产、执行入口、总线现实组织起来
- 让系统先能跑，再谈更重的插件化包装

---

## 2. 借壳生蛋的原则

Claude Code 的 `.claude/` 目录哲学启发很强，但 GM-LITE 不应简单复制品牌语义。

正确吸收方式是：

- 借用“文件即界面、目录即基础设施”的思想
- 不把系统命名和边界完全绑死在单一厂商工具上

因此，GM-LITE 的落地不应是“做 Claude 的镜像”，而是：

> 将目录规范工程化，作为 GM-LITE 自己的轻量外壳模型。  

---

## 3. 外壳与内核的分工

### 3.1 `.gm-lite/`

`.gm-lite/` 是：

- 规则层
- 资产层
- 命令层
- 组织层

它负责回答：

- 系统有哪些宪法与规则？
- 哪些技能资产是合格成品？
- 军团分工怎么定义？
- 哪些命令可以触发运行？

### 3.2 `.gm_bus/`

`.gm_bus/` 是：

- 共享任务现实层
- 运行时状态层
- dispatch / receipt / writeback / escalation 事实源

它负责回答：

- 当前任务发生了什么？
- 哪些任务已投递？
- 哪些回执已到？
- 哪些写回已完成？
- 哪些异常已升级？

### 3.3 统一关系

因此：

> `.gm-lite/` = 产品外壳  
> `.gm_bus/` = 运行时内核  

两者不能混为一谈，也不能互相替代。

---

## 4. 推荐的最小目录外壳

GM-LITE Light 的推荐最小目录结构如下：

```text
.gm-lite/
  constitution/
  rules/
  skills/
  agents/
  commands/
  templates/

.gm_bus/
  manifest.json
  outbox/
  inbox/
  writeback/
  escalation/
  archive/
```

---

## 5. 各目录职责

### 5.1 `constitution/`

职责：

- 存放 GM-LITE 的总宪法
- 定义上位原则、不可突破边界、系统级禁令

它更适合 GM-LITE 自己的中立语义，不强依赖某个插件品牌。

### 5.2 `rules/`

职责：

- 存放 Contract / Spec / Gate / 校验规则
- 存放 JSON / YAML / Schema / Predicate Checklist

它是“法律条文”的机器可读层。

### 5.3 `skills/`

职责：

- 存放已经通过门禁的稳定技能资产
- 只有通过共享总线、门禁链和测试链的产物，才允许进入此目录

它是“成品库”，不是实验场。

### 5.4 `agents/`

职责：

- 定义不同模型 / 军团成员的角色分工
- 记录执行 / 审查 / 合规 / 门禁 / 影子审计等职责

它是“军团编制表”。

### 5.5 `commands/`

职责：

- 存放 watchman / watchdog / CLI 命令脚本
- 存放一键触发：
  - 监听总线
  - 拉起执行
  - 做门禁
  - 固化产物

它是“运行时触发层”。

### 5.6 `templates/`

职责：

- 存放 Task Envelope、Contract、Checklist、Writeback、Report 模板

它用于减少人工拼装成本，稳定结构化产物的形状。

---

## 6. 文件即界面

GM-LITE Light 的现实落地，不需要先依赖复杂插件 UI。

先用：

- 目录结构
- 宪法文件
- 规则文件
- 命令脚本
- 共享总线

来形成一个可运行系统。

这意味着：

> 配置即基础设施（Configuration as Infrastructure）。  

用户不必先等到完整 UI 才能获得工业化收益。

---

## 7. 为什么这条路线能解绑当前困境

当前主要困境有两个：

1. 插件 UI 研发成本高  
2. 人肉搬运和人工调度成本高  

目录外壳模型可以同时缓解这两点：

- 先不做重 UI，避免“开发者悖论”
- 把系统能力尽可能下沉到：
  - 规则
  - 文件
  - 总线
  - 命令

从而使 Light 版先跑起来。

---

## 7.1 与“虚胖插件方案”的差异

GM-LITE 当前明确放弃的，不是插件本身，而是：

- 先做重 WebView
- 先做复杂交互壳
- 先把自然语言当唯一输入
- 先把插件 API 当唯一通信层

转而采用：

- `.gm-lite/` 作为规则与资产外壳
- `.spec / Contract / Checklist` 作为强约束输入
- 专家分工齐射作为执行编制
- `.gm_bus` 作为共享任务总线
- 7B 静态审计 + 物理沙箱作为准入门禁

这意味着：

> Light 版先解决“系统能否稳定生产”，  
> 而不是先解决“界面像不像完整插件”。  

---

## 8. 与现有主线的关系

本模型不是替代当前 GM-LITE 主线，而是给主线提供现实落地壳。

它与现有主线的关系如下：

- `.gm_bus` 主线：提供共享任务现实层
- `controller console` 主线：提供主控官视角
- `dispatch assist` 主线：提供派发与追件能力
- `directory shell model`：提供产品外壳与组织载体

因此它是：

> 外壳模型，不是竞争模型。  

---

## 9. 当前结论

本文件正式冻结以下判断：

1. GM-LITE Light 不应优先投入重插件 UI
2. `.gm-lite/` 应作为规则、资产、命令与组织层外壳
3. `.gm_bus/` 应继续作为唯一运行时共享任务现实层
4. “文件即界面、目录即基础设施”是当前最现实的落地壳
5. 目录外壳路线是对当前插件复杂度问题的有效解绑方案
