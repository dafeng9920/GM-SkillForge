# GM-LITE 信架构不信 AI V1

## 1. 核心立场

GM-LITE 的核心转向不是继续追求“更聪明的 AI”，而是建立：

> 不信 AI，信架构。

含义如下：

- AI 可以生成候选产物，但不能自证合法。
- 合法性不来自模型解释，而来自契约、结构、门禁、测试与回放。
- 系统只接纳通过物理规则与架构规则双重审计的产物。

---

## 2. 核心痛点与对应解法

| 核心痛点 | 解决方案 | 关键落地手段 |
|---|---|---|
| 高昂 Token 成本与冗余 | 1130 近防炮式分级架构 | GPT-5.4/Codex 指挥，GLM 军团齐射，本地 7B 锁闭 |
| 7B 智力不足导致卡壳 | 去自然语言化 | 谓词化 Checklist、正则、AST、Schema 校验 |
| 跨插件通信摩擦 | 基于文件的消息总线 | 统一共享总线目录，Nonce/时间戳/状态清单 |
| AI 假装完成与逻辑漂移 | 架构主权 | Contract-First、反向语义回声、结构指纹审计 |
| 多 Agent 协作吵架 | 非对称验证 | 沙箱测试、静态断言、架构判据为唯一真理 |

---

## 3. 三位一体算力架构

### 3.1 指挥层

由 Codex / GPT-5.4 承担。

职责：

- 将自然语言需求降级为 `.spec` 与 `Contract.json`
- 输出谓词化检查对象，而不是模糊任务描述
- 冻结数据流、边界、副作用与禁止项
- 不直接给执行层解释权

指挥层产物不是“请写个函数”，而必须是：

- `Contract.json`
- `Checklist.json`
- `DataFlowMap`
- `AllowedSideEffects`
- `ForbiddenSideEffects`

### 3.2 执行层

由 GLM 军团或其他执行 Agent 承担。

职责：

- 在受控沙箱中实现代码
- 只对契约负责，不对全局自由发挥
- 自愈只能在契约约束内进行
- 交付的是候选代码，不是最终真理

### 3.3 门禁层

由本地 7B + 静态工具承担。

职责：

- 谓词清单勾验
- AST / Schema / Type Hint / 禁止调用扫描
- 反向语义推导粗筛
- 结构指纹比对
- 触发测试与熔断

门禁层不是“聪明法官”，而是“物理卡尺”。

---

## 4. Contract-First：架构输出即法律

### 4.1 原则

架构层输出必须先于代码。

代码不得先写，再倒推需求；必须先有契约，再生成实现。

### 4.2 Contract 最小结构

`Contract.json` 至少应包含：

- `inputs`
- `outputs`
- `data_flow`
- `allowed_side_effects`
- `forbidden_side_effects`
- `error_handling_requirements`
- `type_expectations`
- `non_goals`

### 4.3 判定逻辑

如果代码出现以下任一情况，则直接视为假输出：

- 出现 Contract 未允许的副作用
- 缺失 Contract 明确要求的异常处理
- 输入输出边界不匹配
- 引入禁止模块或禁止调用
- 数据流节点次序违反契约

此时系统直接熔断，不听模型辩解。

---

## 5. Structural Shadowing：不看作文，看骨架

### 5.1 原则

避免让不同模型围绕“这段代码像不像需求”进行自然语言吵架。

真正核准对象应为：

- 逻辑骨架
- 关键分支
- 状态变更顺序
- 副作用节点位置

### 5.2 双树来源

指挥层应输出：

- `LogicTree`
- `PseudocodeFlow`

门禁层应提取：

- AST
- CFG（可选）
- 关键结构指纹

### 5.3 结构比对不是全文同构

GM-LITE 不要求完整树形完全一致，而要求关键结构一致：

- 关键条件分支存在
- 关键循环 / 重试 / 回滚节点存在
- 副作用发生位置正确
- 禁止结构未出现

只要关键结构指纹偏离，即可判定逻辑漂移风险。

---

## 6. 真输出标准：测试通过只是必要条件

### 6.1 原则

未通过测试的代码，不是产物，只是候选。

但测试通过也不是唯一合法性来源，必须与架构审计共同成立。

### 6.2 GM-LITE 中的真输出定义

一个候选实现只有在以下条件全部满足时，才可进入插件视图：

1. Contract 审计通过
2. 谓词化 Checklist 通过
3. AST / Schema / Type 检查通过
4. 关键结构指纹对齐
5. Hard Test Suite 通过
6. 未触发禁止副作用规则

最终合法性来源是：

> 架构约束 + 物理测试 + 静态门禁 的交集。

---

## 7. 非对称验证：不允许 AI 平等辩论

GM-LITE 中不同层级的权力不是平等的。

### 7.1 执行层

执行层是被告，只负责提交：

- 代码
- 测试结果
- 运行日志
- 修复尝试

### 7.2 门禁层

门禁层负责搜身与判定：

- 是否越界
- 是否偏离契约
- 是否触发禁止项

### 7.3 架构层

架构层是法典来源。

架构层不参与与执行层争辩，只定义规则：

- 什么是合法
- 什么是非法
- 什么必须打回

因此，GM-LITE 的判定结构不是“AI 彼此说服”，而是：

> 执行层交证据  
> 门禁层做审计  
> 架构层给法典

---

## 8. 反向语义回声：辅助核准，不是唯一裁决

反向语义推导仍然有价值，但它不是最终真理。

它适合作为：

- 粗筛
- 风险预警
- 偏题发现器

推荐的四层核准顺序：

1. Tag Cloud Matching
2. I/O + Side Effect Assertions
3. Consensus Scoring
4. Structural Alignment

其中最终主裁决应优先依赖：

- I/O 边界
- 副作用断言
- 结构指纹

而不是自由语言解释。

## 9. 共享总线命名统一

当前已有冻结主线为：

- `.gm_bus`

因此本文件中提到的：

- `.forge_sync`

只能被视为概念上的“共享状态目录”意图，不作为新的权威总线命名。

### 9.1 统一规则

GM-LITE 当前唯一权威共享任务总线命名为：

- `.gm_bus`

后续若需要兼容：

- `.forge_sync`

只能作为别名、兼容层或迁移说明出现，不允许与 `.gm_bus` 并列成为第二总线。

### 9.2 原因

若同时保留两个总线命名，会导致：

- 权威路径混乱
- 读写源混乱
- 插件适配器目标不唯一
- verification 与 writeback 口径分裂

因此：

> 共享任务现实层统一以 `.gm_bus` 为准。

---

## 10. Architecture Heartbeat

GM-LITE 后续必须具备一个持续性一致性扫描能力。

其目标不是做复杂 AI 判断，而是周期性检查：

- 当前产物是否偏离 Contract
- 是否出现新的禁止副作用
- 是否存在结构漂移
- 是否存在 writeback 缺件
- 是否存在总线状态异常

建议工程名：

- `architecture_consistency_scanner`

它是未来 Core 版本的重要演进方向，但 Light 版应先至少冻结其接口与判据。

---

## 11. 对 GM-LITE 的实际意义

这一套原则落地后，GM-LITE 的角色会发生根本变化：

- 用户不再是代码审批员
- 主控官不再是人工中继器
- AI 不再靠解释争取通过
- 系统开始以规则、结构、测试和总线为中心运转

换句话说：

> GM-LITE 不是“让 AI 更会说”。  
> GM-LITE 是“让系统不依赖 AI 的说法”。  

---

## 12. 当前结论

本文件作为 GM-LITE 的上位架构宣言之一，正式冻结以下共识：

1. 不信 AI，信架构
2. Contract-First 优先于自然语言任务描述
3. 测试通过是必要条件，不是唯一条件
4. 关键结构指纹对齐优先于自由解释
5. 共享任务现实层统一命名为 `.gm_bus`
6. 非对称验证是多 Agent 生产的基本制度
7. 架构一致性扫描是后续必须建设的系统能力
